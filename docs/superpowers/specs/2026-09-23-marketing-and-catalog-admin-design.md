# Реклама, акции, карточка товара в админке, рейтинг товаров — дизайн

Дата: 2026-09-23. Статус: на согласовании с владельцем.

Пять связанных, но независимых частей. Каждая реализуется и проверяется отдельно (см. «Разбивка на
планы» в конце), но описаны здесь вместе, потому что вопросы по ним обсуждались в одной сессии и местами
пересекаются данными (товар, филиал, права).

## 0. Что уже есть в проекте и переиспользуется

- **Поиск товара**: `GET /api/products?q=` (ищет по названию/бренду/описанию/характеристикам; в `admin/catalog`
  отдельно ищет ещё и по артикулу) — для баннеров/акций дополню customer-facing поиск артикулом тоже.
- **Загрузка изображения**: `AvatarUploader.tsx` — клиент грузит файл прямо в Supabase Storage, получает
  публичный URL, отправляет URL в API, который проверяет префикс пути. Тот же приём для баннеров, новый bucket.
- **Карточка товара со скидкой**: `ProductCard.tsx` уже рисует зачёркнутую цену и «-X%», если у товара есть
  `attributes.oldPrice` больше текущей цены — сейчас это только статичные демо-данные без дат. Карточку не меняю,
  просто передаю в неё товар с уже подставленной акционной ценой.
- **Карусель**: `HeroSlider.tsx` — автопрокрутка, точки, свайп, пауза при касании. Беру за образец механики для
  всплывающего окна баннера (не переиспользую компонент напрямую — там другая форма данных и разметка).
- **Права**: `isStoreManager(role)` = owner/admin (без branch_manager) уже используется для похожих
  стор-вайд разделов (`/admin/feedback` до вчерашней правки). Использую тот же критерий.
- **RLS-паттерн для филиала**: `staff_roles.sql` — управляющий видит/меняет только своё (`p.branch_id = X.branch_id`).
  Использую для рейтинга.
- **«Хит продаж»**: RPC `top_selling_items(p_limit)` — считает количество проданного по заказам (не отменённым),
  без разбивки по филиалам и периоду. Расширяю, а не переписываю.
- **Штрихкод**: колонка `products.barcode` уже существует в БД (добавлена в `00_base_schema.sql`), нигде не
  показывается и не используется. Объём/граммаж: `attributes.volume` уже существует и уже используется для
  фильтров в каталоге. Обе колонки просто не выведены в админке.

## 1. Баннеры

### Данные

Новая таблица `banners` (аддитивный SQL-файл `supabase/marketing.sql`):

```sql
create table public.banners (
  id uuid primary key default gen_random_uuid(),
  store_id uuid not null references public.stores(id) on delete cascade,
  product_id uuid references public.products(id) on delete set null,
  title text not null,               -- одно поле и для списка в админке, и для текста на баннере
  subtitle text,
  image_url text,
  button_text text,
  start_at timestamptz not null,
  end_at timestamptz not null,
  status text not null default 'draft' check (status in ('draft','active','disabled')),
  priority integer not null default 0,  -- меньше = показывается раньше
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

`product_id` — `on delete set null`: если товар удалён, баннер не пропадает из истории/списка в админке, но
перестаёт быть кликабельным для клиента (см. «Клиентская сторона» ниже) и в списке админки помечается как
«Требует внимания — товар удалён».

RLS: SELECT — любой профиль того же `store_id` (клиенты тоже читают, иначе баннер не показать); INSERT/UPDATE/DELETE
— только `role in ('admin','owner')`. Storage bucket `banners` — публичное чтение, запись только staff (тот же
принцип, что у `avatars`, но без персональной папки на пользователя — папка на магазин: `{store_id}/{uuid}.jpg`).

### Статус и «завершённость» — без крона

Хранится только то, что задал администратор: `draft` / `active` / `disabled`. «Активен, но период ещё не начался»
и «Активен, но период уже прошёл» — не отдельные статусы в БД, а вычисляются одной функцией на чтении:

```ts
// src/lib/promo-status.ts
type EffectiveState = "draft" | "scheduled" | "active" | "expired" | "disabled";
function effectiveState(row: { status: string; start_at: string; end_at: string }, now = new Date()): EffectiveState
```

Используется и в API (что видит клиент — только `effectiveState === "active"`), и в админке (какой бейдж
показать в списке — «Черновик» / «Запланирован» / «Активен» / «Завершён» / «Отключён»). Один источник правды,
ничего не рассинхронизируется, никакой фоновой задачи не нужно.

### Админка

- Новый пункт меню «📢 Реклама и акции» (`MessageSquare`-подобная иконка, например `Megaphone`) — виден только
  owner/admin (как сейчас `/admin/staff` виден только owner — паттерн уже есть).
- Маршрут `/admin/promo?tab=banners|promotions`, две вкладки.
- Вкладка «Баннеры»: список карточками — превью картинки, `title`, товар (мини-превью), бейдж статуса, даты,
  приоритет, действия (редактировать / предпросмотр / отключить / удалить). Фильтр Все/Активные/Черновики/Завершённые
  (по `effectiveState`).
- Кнопка «➕ Создать баннер» → форма: `title`, `subtitle`, изображение (клиентский аплоад, сжатие до разумного
  размера перед загрузкой — тот же приём, что в `AvatarUploader`, но без обрезки в квадрат: баннер широкий,
  как `HeroSlider`, пропорция 16:11), поиск товара (см. ниже — общий компонент), `button_text`, даты начала/конца,
  статус, приоритет (число). Кнопка «Предпросмотр» — открывает тот же компонент, что рисует баннер клиенту
  (`BannerInterstitial`), с текущими (ещё не сохранёнными) данными формы.
- **Общий компонент поиска товара** `ProductPicker.tsx` — переиспользуется баннерами и акциями. Поле ввода с
  debounce → `GET /api/products?q=...` (добавляю поиск по артикулу в этот эндпоинт) → список найденных
  (фото/бренд/название/цена) → клик выбирает, дальше используется `product.id`, `product.name`, `product.brand`,
  `product.imageUrl`, `product.price` только для показа в форме — единственный источник истины остаётся таблица
  `products`.

### Клиентская сторона

Не карусель на главной (она остаётся как есть, без изменений) — **всплывающее модальное окно**, показывается:

1. при первом за это открытие приложения переходе на `/catalog`;
2. при первом за это открытие приложения переходе на `/checkout`.

Использую тот же приём, что для `BuyAgainPrompt`/`session-flags.ts` (sessionStorage-флаг, не localStorage — значит
не переживает закрытие приложения, ровно как остальные ненавязчивые подсказки в этой сессии). Показывается
баннер с наименьшим `priority` среди активных (`effectiveState === "active"`) для магазина; если баннеров с
одинаковым наивысшим приоритетом несколько — берём любой (например, первый по `created_at`), это не критично.

`BannerInterstitial.tsx` — модалка с переливом `tile-sheen` (как у `BuyAgainModal`): картинка, `title`, `subtitle`,
кнопка `button_text` (или дефолтный текст, если пусто). Клик по карточке (не по крестику) → переход на
`/product/{product_id}`. Крестик → просто закрыть. Если `product_id` у баннера `null` (товар был удалён) —
баннер не показывается вовсе (пропускается при выборе, без ошибки).

## 2. Акции

### Данные

Та же миграция `supabase/marketing.sql`:

```sql
create table public.promotions (
  id uuid primary key default gen_random_uuid(),
  store_id uuid not null references public.stores(id) on delete cascade,
  product_id uuid references public.products(id) on delete set null,
  title text not null,
  discount_type text not null check (discount_type in ('percent','fixed','special_price')),
  discount_value numeric,        -- % или сом-сумма скидки (не используется при special_price)
  old_price numeric not null,    -- снимок цены товара на момент создания/редактирования акции
  new_price numeric not null,    -- вычисленная или введённая новая цена
  show_old_price boolean not null default true,  -- показывать ли old_price зачёркнутой и «-X%»
  start_at timestamptz not null,
  end_at timestamptz not null,
  status text not null default 'draft' check (status in ('draft','active','disabled')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

`old_price`/`new_price` считаются на сервере при сохранении формы (не на клиенте, чтобы нельзя было подменить):
- `percent`: `new_price = round(product.price * (1 - discount_value/100))`
- `fixed`: `new_price = product.price - discount_value`
- `special_price`: `new_price = discount_value` (в этом режиме поле называется в форме «Новая цена», не «Скидка»)

`old_price` = текущая `product.price` на момент сохранения (снимок, не пересчитывается автоматически, если
владелец потом поменяет базовую цену товара, пока акция активна — осознанное упрощение, отмечаю явно: если
нужно, чтобы акция всегда пересчитывалась от актуальной цены, это отдельная небольшая правка после первого
запуска).

`show_old_price` — новая галочка «Показывать старую цену зачёркнутой» (по запросу владельца). В базе колонка по
умолчанию `true`. В форме создания галочка предзаполняется по типу скидки — включена для «процент»/«фиксированная
сумма» (это и есть суть акции — показать выгоду), выключена для «новая цена» (обычно это просто смена цены без
вида «акции») — это только стартовое положение галочки в форме, сама галочка одна и та же для всех трёх типов, и
админ может переключить её в любую сторону независимо от выбранного типа скидки.

RLS — как у `banners` (SELECT — весь магазин, запись — admin/owner).

### Применение цены — везде, не только в блоке «Акции»

Общий хелпер `src/lib/apply-promotion.ts`:

```ts
function applyActivePromotion(product, activePromotionsByProductId): Product
// если есть активная (effectiveState === "active") акция на этот товар:
//   product.price = promotion.new_price
//   если promotion.show_old_price: product.attributes.oldPrice = promotion.old_price
//   иначе: product.attributes.oldPrice не выставляется (обычная цена без зачёркивания)
```

Используется в трёх местах на сервере: `GET /api/products` (список/каталог/поиск), `GET /api/products/[id]`
(страница товара), `GET /api/promotions` (блок «Акции» на главной). Один расчёт, три точки применения — цена не
может «разъехаться» между каталогом и блоком акций. `ProductCard` и страница товара не меняются вообще: они уже
умеют рисовать `oldPrice`/скидку, если она есть в объекте товара.

Из-за этого скидка автоматически попадает и в корзину, и в заказ (там цена берётся из объекта товара на момент
добавления в корзину, как и сегодня с любой ценой) — ничего в `cart-context.tsx`, `checkout` и создании заказа
менять не нужно.

### Админка

Вкладка «Акции» в том же `/admin/promo`: кнопка «➕ Создать акцию» → сначала `ProductPicker` (тот же компонент,
что у баннеров), после выбора товара — форма: `title`, тип скидки (переключатель: процент / фиксированная сумма /
новая цена — при выборе показываются разные поля ввода), даты, статус, галочка «Показывать старую цену
зачёркнутой», и живой предпросмотр цены прямо в форме («Было 500 сом → Станет 400 сом, -20%») по мере ввода.
Список акций — как у баннеров: карточки/таблица «Акция | Товар | Скидка | Статус | Начало | Окончание | Действия»,
те же фильтры и действия (редактировать/просмотр/отключить/удалить).

### Главная страница — блок «🔥 Акции»

Новая секция на главной, в том же стиле, что «Популярные товары» (`Section` + горизонтальная лента или сетка
из `<ProductCard>`), показывает товары с активной акцией (через `GET /api/promotions`). Если активных акций нет —
блок не рендерится вовсе (не оставляет пустое место). Сортировка — по дате окончания (сначала те, что заканчиваются
раньше — создаёт ощущение «успей купить», частый паттерн у акций).

### Остатки

Ничего нового: `ProductCard` уже скрывает доступность покупки, если `branchQuantity === 0`. Акция на закончившийся
товар просто отображается как обычная карточка «Нет в наличии» — уже так работает.

## 3. Карточка товара в админке: граммаж и штрихкод

Небольшое дополнение к `admin/catalog` (`src/app/[locale]/(app)/admin/catalog/page.tsx`) и `GET /api/admin/catalog`:
- В ответ API добавляется `barcode` (сейчас нигде не отдаётся, хотя колонка есть) и объём — уже приходит как
  `attributes.volume`, просто не выводится в этой таблице.
- В таблицу добавляются две колонки: «Штрихкод» и «Объём/вес». Только показ, без редактирования — в проекте

## 4. Рейтинг товаров (по продажам)

Не звёздочки от покупателей — расширение уже существующего «Хит продаж» (посчитано автоматически из заказов).

### База

Расширяю существующую функцию (аддитивно, `create or replace`, старые вызовы продолжают работать без изменений —
у новых параметров есть значения по умолчанию):

```sql
create or replace function public.top_selling_items(
  p_limit int default 12,
  p_branch_id uuid default null,   -- null = все филиалы вместе
  p_since timestamptz default null -- null = за всё время
)
returns table (name text, brand text, total_qty bigint)
...
  where o.status <> 'cancelled'
    and (p_branch_id is null or o.branch_id = p_branch_id)
    and (p_since is null or o.created_at >= p_since)
```

Разграничение по ролям — не внутри SQL-функции (она осталась security definer и «доверяет» параметрам), а в новом
API-роуте, как везде в проекте: `GET /api/admin/product-rating?branchId=...&period=week|month|all`.
- `isStaff(role)` — доступ только персоналу (owner/admin/branch_manager), не покупателям.
- Если `role === 'branch_manager'` — `branchId` из запроса ИГНОРИРУЕТСЯ, всегда подставляется `profile.branchId`
  (даже если в URL передали чужой филиал) — управляющий физически не может увидеть чужой рейтинг или общий.
- Если `role in ('admin','owner')` — `branchId` берётся из запроса как есть; отсутствует/`all` = `null` (весь
  магазин).
- `period` → `since`: `week` = `now() - 7 days`, `month` = `now() - 30 days`, `all`/отсутствует = `null`.

### Админка

Новый пункт меню (отдельная иконка, например `Star` или `TrendingUp`) «Рейтинг товаров», виден всем трём ролям
(owner/admin/branch_manager — в отличие от рекламы, тут именно управляющему и нужно это видеть про свой филиал).
Страница `/admin/rating`:
- owner/admin видят переключатель периода (Неделя/Месяц/Всё, по умолчанию «Всё») и переключатель филиала
  («Все филиалы» + список филиалов).
- branch_manager видит только переключатель периода — переключателя филиала нет вообще (не «выключен», а
  физически не показан в интерфейсе, раз он всё равно не может им воспользоваться).
- Список: место (#1, #2…), фото/название/бренд, количество продано за выбранный период.

## 5. Отзывы и звёзды на странице товара

Третья и отдельная тема — не «Хит продаж»/рейтинг из раздела 4 (тот по продажам, для админки), а настоящие
отзывы от покупателей: звёзды + текст, видны любому на странице товара.

### Данные

Та же миграция (или отдельный файл `supabase/product_reviews.sql` — решу при реализации, не принципиально):

```sql
create table public.product_reviews (
  id uuid primary key default gen_random_uuid(),
  store_id uuid not null references public.stores(id) on delete cascade,
  product_id uuid not null references public.products(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  order_id uuid not null references public.orders(id) on delete cascade,
  rating integer not null check (rating between 1 and 5),
  comment text,
  created_at timestamptz not null default now(),
  unique (order_id, product_id)
);
```

`order_id` — это и есть подтверждение покупки, и естественный способ разрешить «несколько отзывов»: один отзыв
на одну покупку этого товара. Если клиент заказывал товар дважды в разных заказах — может оставить два отзыва,
по одному на каждый. Повторно отзыв на тот же заказ+товар — нельзя (уникальный индекс).

RLS:
- SELECT — весь магазин (отзывы публичные для всех вошедших, как и сами товары).
- INSERT — `user_id = auth.uid()`, и обязательно должен существовать `orders` этого пользователя с этим
  `order_id`, статусом не `cancelled` и этим `product_id` внутри `items_json` (проверка в самой политике через
  `exists (...)`, как уже сделано для `feedback_insert_own`).
- DELETE — `user_id = auth.uid()` (может удалить свой) ИЛИ `role in ('admin','owner')` (может удалить любой).
- UPDATE — не нужен: чтобы «исправить» отзыв, проще удалить свой и написать заново (то же разрешение уже есть).

### Кнопка «Оставить отзыв» на странице товара

Внизу страницы товара, под уже существующими блоками («Описание»/«Похожие товары»). Новый компонент
`ProductReviews.tsx`:
- Наверху — средняя оценка и количество («4.6 ★ · 12 отзывов»), если отзывов пока нет — просто не показывается
  (без «0 отзывов», чтобы не выглядело пусто).
- Список отзывов: звёзды, текст, автор (`display_name` или «Покупатель», как в остальных местах приложения), дата.
- Кнопка «Оставить отзыв»: если у клиента есть хотя бы один свой некэнселенный заказ с этим товаром, ПО
  которому ещё нет отзыва — кнопка активна, открывает маленькую форму (звёзды-переключатель 1–5, необязательный
  текст). Если заказов с этим товаром вообще нет — кнопка видна, но неактивна, с подсказкой «Доступно после
  покупки этого товара». Если все свои заказы этого товара уже отрецензированы — кнопка тоже неактивна с
  подсказкой «Вы уже оставили отзыв по всем своим покупкам этого товара».
- Владелец/админ (`isAdmin` из `useSession`, уже используется по всему приложению) видит рядом с каждым чужим
  отзывом маленькую иконку удаления — без отдельного экрана модерации в админке, всё прямо на странице товара.
  Автор тоже видит эту иконку на своём отзыве.

**Явно вне рамок этой части** (чтобы не расширять незаметно): средняя оценка НЕ выводится на карточке товара в
каталоге/поиске (`ProductCard`) — только на самой странице товара. Если захотите звёзды и там — это небольшое,
отдельное дополнение уже после того, как заработает база.

## Известные компромиссы (проговорить явно)

1. `old_price` акции — снимок на момент сохранения, не пересчитывается, если базовая цена товара потом меняется
   вручную в каталоге, пока акция активна.
2. Приоритет нескольких баннеров с ОДИНАКОВЫМ числом приоритета — какой из них показывается первым, не
   гарантируется (не критично для однозначного числового приоритета, если админ задаёт разные числа).
3. `top_selling_items` по-прежнему сопоставляет позиции заказа с товаром по имени+бренду, а не по `product_id`
   (так было устроено до этой работы, не переделываю) — если товар переименован после того, как его заказывали
   под старым именем, старые заказы могут не попасть в подсчёт «Хит продаж»/рейтинга. Существующее ограничение,
   не новое.
4. Отзыв нельзя отредактировать — только удалить свой и написать заново (по той же покупке: `unique(order_id,
   product_id)` не даст оставить второй на тот же заказ, значит старый сначала удаляется).

## Разбивка на планы реализации

Слишком много для одного плана — разбиваю на три независимых плана, каждый — свой цикл (план → реализация →
проверка):

- **План А — Реклама и акции**: разделы 1, 2 и 3 (баннеры, акции, граммаж/штрихкод в админке — маленькое, но
  того же слоя «каталог + админка», логично сделать заодно).
- **План Б — Рейтинг товаров (по продажам)**: раздел 4, отдельно (не связан данными с рекламой, трогает только
  `top_selling_items` и новую страницу `/admin/rating`).
- **План В — Отзывы и звёзды покупателей**: раздел 5, отдельно (не связан ни с рекламой, ни с рейтингом по
  продажам — своя таблица, своя страница товара).
