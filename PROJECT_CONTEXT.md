## Новая система импорта товаров — 15.09

Старая загрузка (Каталог → выбрать файл → всё сразу заменяется) заменена на мастер:
выбор файла → определение колонок (автоматически + ручная правка) → предпросмотр →
подтверждение → импорт. Раздел: `/admin/import`, кнопка "Загрузить товары" на `/admin`.

**Архитектура (специально расширяемая под будущие форматы/магазины):**
- `src/lib/import/formats/` — парсеры конкретных форматов, каждый превращает файл в
  простую таблицу `{headers, rows}`. Сейчас только `xlsx.ts` (Excel/.xls/.xlsx). Чтобы
  добавить CSV или другой формат в будущем — один новый файл здесь + одна строка в
  `formats/index.ts`, остальной код (автоопределение колонок, валидация, сам UI) трогать
  не нужно.
- `src/lib/import/fields.ts` — список полей Beauty (Название, Цена, Артикул, Остаток,
  Бренд, Категория, Описание, Характеристики, Для кого/чего, Фото) с синонимами для
  автоопределения. Чтобы научить систему понимать новое название колонки — добавить
  строку в список алиасов нужного поля.
- `src/lib/import/autoMap.ts`, `validate.ts` — автоопределение колонок по заголовкам +
  построчная проверка (отсутствует название, некорректная цена, дубликат артикула).

## Регистрация/авторизация — реальные баги найдены и исправлены (14.09)
Пользователь сообщил: после нажатия "Зарегистрироваться" приложение молча кидало на
"Войти", письмо подтверждения при повторных попытках не приходило. Разобрано по логам
Supabase (`auth_logs`), найдены ДВЕ настоящие причины (не косметика):

1. **Supabase возвращает "успех" без ошибки и БЕЗ письма, если email уже
   зарегистрирован** (так задумано — защита от перебора email). Старый код не отличал
   этот случай от настоящей новой регистрации и всегда показывал "Мы отправили
   письмо…", даже когда письмо не отправлялось. Исправлено: `src/app/(auth)/login/page.tsx`
   теперь проверяет `data.user.identities.length === 0` и показывает честное сообщение
   "Этот email уже зарегистрирован. Войдите в аккаунт или восстановите пароль." —
   подтверждено вживую в браузере.
2. **Роль "owner" присваивалась первому, кто просто НАЖАЛ "Зарегистрироваться", а не
   первому, кто реально подтвердил email.** Из-за этого `eramyrza0028@gmail.com`
   (тестовая попытка, email так и не подтверждён, ни разу не логинился) навсегда занял
   `owner`, а настоящий `famermishall@gmail.com` (подтверждён, входил в систему) получил
   обычную роль `user`. Исправлено миграцией `fix_owner_assignment_on_email_confirm` в
   Supabase: `owner` теперь назначается ПОСЛЕ подтверждения email (новый триггер
   `on_auth_user_confirmed`), и роли двух существующих аккаунтов исправлены вручную
   (famermishall → owner, eramyrza → user).

- `signUp`/`resend` теперь явно передают `emailRedirectTo` на текущий origin (раньше

- Добавлена проверка сессии на `/login` при загрузке страницы (`getSession()`) — если
  пользователь пришёл по ссылке подтверждения из письма (токен в URL fragment, который

## Что это
Веб-приложение (сайт, работающий и на телефоне, и на компьютере) для магазина.
Покупатель пишет, что ищет, — AI подбирает товары ТОЛЬКО из реального каталога магазина.
Заказ оформляется без онлайн-оплаты и без доставки от AI: покупатель выбирает филиал,
оставляет имя/телефон, и заказ уходит продавцу в WhatsApp этого филиала.

Приложение закрыто авторизацией: без входа в систему интерфейс вообще не открывается —
сначала экран входа/регистрации.

## Система авторизации и ролей

### Модель данных
- `auth.users` — встроенная таблица Supabase Auth (email, пароль).
- `public.profiles` — по одной строке на пользователя: `role` (`user` | `admin` | `owner` |
  `super_admin`), `store_id`. Создаётся триггером `handle_new_user` (AFTER INSERT ON
  auth.users) с ролью `user` по умолчанию.
- **Владельцем (`owner`) становится первый пользователь, который ПОДТВЕРДИЛ email**
  (не просто нажал "Зарегистрироваться") — назначается триггером `on_auth_user_confirmed`
  (AFTER UPDATE ON auth.users, когда `email_confirmed_at` становится не-null), см. раздел
  про исправление багов выше. Все следующие подтверждённые пользователи — обычные `user`.
- Роли `admin` и `owner` обе дают доступ к `/admin`; только `owner` может передать
  владение магазином другому человеку (важно для будущей продажи системы разным
  магазинам — см. ниже).

### Разграничение доступа — по-настоящему, не только в интерфейсе
1. `src/proxy.ts` (замена middleware.ts в Next.js 16) — на каждый переход по странице
   проверяется сессия Supabase. Нет сессии → редирект на `/login`.
2. `src/app/(app)/admin/layout.tsx` — серверная проверка роли на КАЖДЫЙ запрос к
   `/admin/*`. Не admin/owner → редирект на `/?denied=admin` (баннер "Доступ запрещён").
3. Каждый API-маршрут сам проверяет сессию (`getSessionProfile()`) и сам определяет
   `store_id` пользователя — клиент не может передать чужой storeSlug.
4. RLS-политики в самой базе данных (последняя линия защиты): товары/филиалы/заказы
   видны только своему магазину; писать могут только admin/owner своего магазина.

### Экраны
- `/login` — одна страница, три вкладки (Войти / Регистрация / Забыли пароль).
- `/reset-password` — по ссылке из письма, форма нового пароля.
- Splash-экран (0.9 сек) с названием магазина при каждом входе/открытии приложения.
- `/admin/settings` — смена email (с подтверждением по почте), смена пароля, и (только
  у owner) передача владения магазином другому зарегистрированному пользователю по email.

### Передача владения магазином (для продажи разным клиентам в будущем)
SQL-функция `transfer_store_ownership(new_owner_email)` в Supabase: владелец вводит email
УЖЕ зарегистрированного человека — тот становится owner магазина, прежний владелец
полностью теряет доступ (role→user, store_id→null). Так тестовый аккаунт (моя личная
почта) можно будет безопасно "отвязать" после продажи, не трогая код/базу вручную.
Ограничение: новый владелец должен СНАЧАЛА сам зарегистрироваться (нет доступа к
Supabase Admin API, чтобы создавать аккаунты за других людей).

## Роли: управляющий филиала, сотрудники, один аккаунт — два режима (21.09)
- Роли: `owner` (всё), `admin` (весь магазин, кроме «Сотрудников»), **`branch_manager`** (только свой
  филиал: остатки и заказы + «Аккаунт»), `user` (покупатель). Новые люди всегда `user`; доступ выдаёт
  только владелец в разделе **«Сотрудники»** (`/admin/staff`, `/api/admin/staff`): вводит почту
  (человек должен сначала сам зарегистрироваться) + роль + филиал; «Снять доступ» → снова `user`.
- БД: `supabase/staff_roles.sql` (ЗАПУСТИТЬ в SQL Editor, без переводчика браузера): колонка
  `profiles.branch_id`, роль `branch_manager` в check-ограничении, функции `staff_list` /
  `staff_set` (security definer, только владелец, сообщения об ошибках по-русски), RLS-политики
  «управляющий видит/правит остатки и заказы только своего филиала», триггер, сам пересчитывающий
  `products.in_stock` при изменении остатков (управляющий не может править таблицу товаров).
  Код читает `branch_id` отдельным запросом только для `branch_manager`, поэтому вход не ломается,
  даже если SQL ещё не запущен.
- Проверки на сервере: `isStaff(role)` (auth.ts) пускает в админку; в `/api/admin/stock` и
  `/api/admin/orders` управляющий принудительно ограничен своим `branchId` (что бы ни прислал клиент);
  остальные админ-API по-прежнему только `owner/admin`. `proxy.ts`: управляющему доступны лишь
  `/admin`, `/admin/stock`, `/admin/orders`, `/admin/settings`; `admin` не открывает `/admin/staff`.
- **Один аккаунт — два режима** (вопрос владельца: у людей одна почта и они хотят и работать, и
  покупать): сотрудник по кнопке «В магазин» (шапка админки) видит витрину как покупатель, по кнопке
  «Админка» возвращается. Реализация: cookie `beautyai-mode=shop` (`src/lib/view-mode.ts`) только
  разрешает `proxy.ts` открывать витрину; реальные права всегда по роли в БД. `isAdmin` в
  `session-context` теперь = «сотрудник на /admin/*», `isManager` = «у человека есть роль сотрудника».
  Заказы, сделанные в режиме покупателя, привязаны к его `user_id` как обычные.

  в админке кнопка «следующий шаг» (Подтвердить → Отметить оплаченным → Передан курьеру → Заказ
  доставлен) + выпадающий список, а в WhatsApp-сообщении филиалу теперь пять ссылок (одно нажатие —
  статус обновился без входа). «Автоматически» без интеграции с платёжной/курьерской системой не
  получится — это возможный следующий этап, когда станет известно, чем они пользуются.
- **Продажи** = заказы со статусом «Оплачен», «Передан курьеру», «Выполнен» (новые, неоплаченные и
  отменённые не входят). Блок «Продажи» вверху страницы заказов: период (сегодня / 7 / 30 дней / всё
  время), итоговая сумма и число заказов. Управляющий филиала видит продажи только своего филиала;
  владелец/админ — все филиалы: таблица «филиал → заказов → сумма» и «Итого по всем филиалам».
  Дата продажи = `paid_at` (если нет — дата создания).
- Заказы: фильтры по статусу (с числами) и, для владельца/админа, по филиалу; пагинация по 30.

  ограничение статусов, функция `set_order_status_by_token` для ссылок из WhatsApp. Код работает и до

- **Как платят и оформляют (решение владельца, 21.09):** покупка и оплата — только через продавца в WhatsApp,

  бейдж «новых заказов» на главной админки — каждые 30 с. В заказе видно, кто и когда отметил статус
  («отметил продавец в WhatsApp» / «отмечено в приложении») — колонки `orders.status_source`,
  `status_changed_at` (в `order_payments.sql`, безопасно перезапускать). Цепочка в админке:
  Новый → Подтверждён → Оплачен → Выполнен; «Передан курьеру» остался необязательным статусом.
  Идея на будущее: WhatsApp Business API (продавец отвечает словом «оплачен» — статус меняется сам) —
  платно и требует одобрения Meta; сейчас не нужно.

## «Очередь заказов»: одна ссылка продавцу, изменение состава, наличие по позициям (21.09)
- Решения владельца (все три «да»): (1) вместо набора ссылок в WhatsApp — **одна ссылка** `/o/<token>`;
  (2) после «Оплата получена» состав **блокируется** (правит только администратор в приложении);
  (3) когда продавец ставит товару 0 — **остаток этого товара в этом филиале автоматически становится 0**
  (только число в приложении; учётная программа не меняется, следующая загрузка Excel может вернуть число —
  продавцу нужно поправить и у себя).
- **Мини-страница продавца** (`/o/<token>`, `OrderConsole.tsx`, API `/api/o/[token]`): состав с кнопками −/+
  (только УМЕНЬШИТЬ, 0 = нет в наличии), итог пересчитывается на глазах, «Сохранить изменения», «Оплата
  получена», «Отменить», «Написать покупателю об изменениях» (WhatsApp с готовым текстом и новой суммой).
  Правила и запись — в SQL-функциях `get_order_by_token` / `edit_order_by_token` (`supabase/order_edit.sql`):
  нельзя добавлять/менять цену, нельзя после оплаты, если убрано всё — заказ отменяется. Старые ссылки
  `/o/<token>/<status>` продолжают работать.
- Данные заказа: позиции хранят `orderedQuantity` (заказано), `productId`, `sku`; `orders.original_total`,
  `edited_at`, `edited_by`. Везде показывается ИТОГОВАЯ сумма: у покупателя («Мои покупки»: убранное
  зачёркнуто «нет в наличии», «было X, стало Y»), у админа/управляющего, в итогах продаж.
- **Админ/управляющий** (`OrderManager.tsx`): рабочая очередь «Требуют действия» (старые сверху), группа «Нет в
  наличии», крупная кнопка «Оплата получена» (из нового/подтверждённого сразу в оплачен), выбор нескольких
  заказов → «Оплата получена (N)», поиск по номеру/имени/телефону, у каждой позиции текущий остаток в филиале
  заказа и жёлтое предупреждение «Проверьте наличие», «Изменить состав» (`PATCH /api/admin/orders/[id]`;
  управляющий — только до оплаты), баннер + звук (кнопка «Включить звук») о новом заказе, заголовок вкладки
  «(N) Заказы». Остаток по позициям считает `attachStock` в `/api/admin/orders` (для старых заказов —
  по названию+бренду).
- **Проверка при оформлении** (`POST /api/orders`): если в выбранном филиале товара точно нет (или меньше, чем
  заказано), заказ не проходит — покупатель видит, чего не хватает, и советуют другой филиал. Нет данных об
  остатке — заказ проходит.
- SQL: `supabase/order_edit.sql` (ЗАПУСТИТЬ; нужен также order_payments.sql). До запуска приложение работает,
  мини-страница сообщает, что нужно запустить SQL.

- Покупатель видит изменения заказа сам: «Мои покупки» обновляются каждые 20 с (и при возврате на вкладку),
  изменённый продавцом заказ помечен жёлтой плашкой «Продавец изменил ваш заказ…», убранное зачёркнуто,

## Заставка выскакивала на каждом переходе на телефоне — исправлено переходом на localStorage+время — 24.09

Владелец проверил анимированную заставку выше на телефоне (Capacitor-обёртка) и сообщил: она выскакивает
при каждом переходе между страницами, а не только один раз при настоящем открытии приложения — «как в
приложении Подружка» (там видео-заставка идёт только при запуске). Причина: флаг «уже показывали» жил в
`sessionStorage` — на вебе этого достаточно (переживает обновления страницы, стирается только с закрытием
вкладки), но в мобильном WebView (Capacitor) страница периодически перезапускается прямо посреди работы с
приложением — при сворачивании или иногда даже при обычной навигации — и такой перезапуск стирает
`sessionStorage`, отчего заставка выскакивала снова, будто это новое открытие (тот же класс проблем, что уже
решался раньше для CART_MARKS_KEY в `session-flags.ts` — комментарий там же).

Решение: `wasSplashShown()`/`markSplashShown()` в `session-flags.ts` переведены на `localStorage` (переживает
такие перезапуски WebView) с меткой времени вместо простого флага — заставка показывается заново только если
с прошлого раза прошло ≥ 20 минут (`SPLASH_REOPEN_GAP_MS`), то есть это действительно новый заход, а не
технический перезапуск WebView посреди работы. Код в `AppSplashGate.tsx` не менялся — только реализация двух
функций, которые он вызывает. Коммит `c3a0b5b`.

Проверено вживую на проде (веб, тестовый аккаунт): свежая регистрация → заставка показалась; сразу после —
полная навигация (`goto`, не просто клик по ссылке) на `/catalog`, имитируя перезапуск страницы — заставка
НЕ появилась повторно, показался только обычный попап нового товара. Полноценно эффект на самом Capacitor
WebView (то, что реально жаловался владелец) в этой сессии не воспроизвести — стоит владельцу самому ещё раз
проверить в приложении на телефоне: открыть, полистать разделы, свернуть и развернуть быстро — заставка не
должна выскакивать; должна появиться снова только если не открывать приложение 20+ минут.

## Заставка выскакивала на pull-to-refresh — добавлено отдельное определение обновления страницы — 24.09

Владелец проверил на телефоне: обновление 20-минутным окном (см. запись выше) не спасло от одного конкретного
случая — жест «потянуть вниз, чтобы обновить» (pull-to-refresh) тоже полноценно перезагружает страницу, и
заставка выскакивала снова, даже если открыл приложение только что. Владелец уточнил чётко: заставка — только
при настоящем входе в приложение, один раз; при обновлении (pull-to-refresh, кнопка «обновить») должно быть в
крайнем случае лёгкое мигание — не заставка.

Решение: `isReloadNavigation()` в `session-flags.ts` — через Navigation Timing API (`performance.getEntriesByType
("navigation")[0].type === "reload"`) отличает именно перезагрузку страницы от настоящего первого захода;
`AppSplashGate.tsx` при обнаружении перезагрузки сразу считает заставку «уже показанной» и не рендерит её вовсе
(в отличие от обычного захода, здесь минимальное время в 1200 мс не выжидается) — независимо от того, сколько
времени прошло с прошлого показа. Коммит `faa484f`.

Проверено вживую на проде: свежая регистрация тестового аккаунта → дождался, пока заставка на главной погасла
→ `location.reload()` (то же самое техническое действие, что делает и pull-to-refresh, и кнопка «обновить») →
скриншот сразу после перезагрузки показал сразу главную страницу без всякой заставки. Тестовые данные удалены.
Сам жест pull-to-refresh именно на телефоне не воспроизвести из этой сессии — стоит владельцу проверить его
отдельно (обычное обновление F5/потянуть вниз не должно показывать заставку никогда, только мигание).

## Заставка всё равно мелькала на обновлении в телефонном браузере — решение перенесено на сервер — 24.09

Владелец проверил на телефоне именно в браузере (Chrome/Safari по ссылке, не в установленном приложении) —
заставка при pull-to-refresh всё ещё выскакивала, хотя дома на компьютере проверка (см. запись выше) проходила
чисто. Причина: прошлое решение («показывать или нет») принималось на КЛИЕНТЕ, уже ПОСЛЕ первой отрисовки —
через `useEffect`, который срабатывает только после того, как браузер уже нарисовал первый кадр. Сервер при
рендере не знает про localStorage/Navigation Timing API, поэтому исходный HTML всегда рисовал заставку видимой
by default — и только потом клиентский код её прятал. На быстром компьютере в Playwright этот промежуток
неразличим на глаз, но на реальном телефоне (более медленный JS, гидратация занимает заметно больше времени)
этот необработанный первый кадр может провисеть на экране достаточно долго, чтобы выглядеть как «заставка
выскочила», даже когда вся логика скрытия технически отработала верно, просто позже, чем успел заметить глаз.

Решение: сама заставка «должна ли показываться» решается теперь на СЕРВЕРЕ, а не на клиенте. Новый файл
`src/lib/splash-cookie.ts` — общая метка времени (`beautyai-splash-last-shown`) и функция `splashRecentlyShown()`,
которой пользуются оба конца: `src/app/[locale]/(app)/layout.tsx` (серверный компонент) читает cookie через
`cookies()` из `next/headers` и передаёт готовое решение `splashAlreadyShown` вниз как пропс, через
`AppProviders.tsx` в `AppSplashGate.tsx` — тот инициализирует своё состояние сразу этим значением
(`useState(initialAlreadyShown)`), а не `false` с последующей правкой в эффекте. Клиент по-прежнему сам пишет
cookie (`document.cookie`) в момент, когда заставка реально была показана и время истекло — но on чтение при
следующей загрузке уже делает сервер. Client-only `wasSplashShown()`/`markSplashShown()`/`isReloadNavigation()`
из `session-flags.ts` убраны полностью — больше не нужны, вся эта логика заменена одним cookie-чтением. Коммит
`304e2e2`.

Проверено вживую на проде: полный цикл (регистрация тестового аккаунта → заставка отыграла → cookie
`beautyai-splash-last-shown` подтверждённо появился в `document.cookie` → `location.reload()`) — и что особенно
важно, проверено не только визуально (скриншот сразу после перезагрузки — заставки нет), но и на уровне
СЫРОГО HTML, который вернул сервер: через Playwright-инструмент `browser_network_request` вытащено тело ответа
на этот самый reload-запрос, и в нём блок заставки УЖЕ присутствует с классами `opacity-0 pointer-events-none`
и `aria-hidden="true"` с самого первого байта — то есть моргнуть просто нечему, даже теоретически, независимо
от скорости телефона. Тестовые данные удалены.

однозначно про действие, а не читается как статус. Коммит `0e4d075`.

## Корзина за аккаунтом + частичное оформление заказа — 29.09

`src/lib/cart-logic.ts` с первыми в проекте автотестами (`npm test`, встроенный node:test через tsx).

ревью: перезагрузка идёт в той же очереди (не затирает только что добавленное), изменения считаются от последнего
состояния («добавить весь набор» не теряет товары), до загрузки корзины изменение сначала берёт её с сервера
(абсолютное количество не затирает серверное), а если какая-то галочка не сохранилась — заказ НЕ отправляется,
клиент видит «Не удалось сохранить изменение».

## Оптовые цены — 29.09

Клиент-магазин: «от 1000 долларов можно оптом набирать (все товары понемногу), от 1000 $ — оптовая цена»; как
именно считает опт — неизвестно, поэтому способ выбирает админ. Спека
`docs/superpowers/specs/2026-09-29-wholesale-pricing-design.md`, план `docs/superpowers/plans/2026-09-29-wholesale-pricing.md`.

**Как работает:** «Магазин» в админке → блок «Оптовые цены»: Выключено / Скидка % на все товары / Своя оптовая
цена у товара; порог в $ + курс доллара (пересчёт «Порог = N сом»). Порог проверяется по сумме ОТМЕЧЕННЫХ товаров по
обычной цене (с акцией); от порога все отмеченные идут по min(обычная с акцией, оптовая). «Своя цена» — колонка
«Оптовая цена» (или «Опт», «Цена опт»…) в Excel-загрузке и синхронизации; товар без неё — по обычной цене. Считает
сервер (`loadCart` + `lib/wholesale.ts`, тесты), клиент показывает тем же кодом. В корзине — полоска «До оптовых цен
осталось N» / «Оптовые цены применены — вы экономите N» (при нулевой экономии не показывается), обычная цена
зачёркнута; на главной — плашка «Опт от 1 000 $ (≈ N сом)»; в каталоге админки колонка «Опт»; у заказа метка «Опт»
(`orders.is_wholesale`), в WhatsApp строка «Оптовый заказ (от N сом)».

**База:** `supabase/wholesale.sql` ПРИМЕНЕНА 29.09 с согласия владельца (stores: wholesale_mode/percent/
threshold_usd/usd_rate; products.wholesale_price; orders.is_wholesale). **Опт сейчас ВЫКЛЮЧЕН** — включает владелец.

**Найдено попутно и исправлено:** автосопоставление колонок Excel могло взять обычную «Цену» из колонки «Оптовая
цена» (слово «цена» в заголовке) — у поля «Цена» теперь есть исключения «опт»/«wholesale» (тест).

**Проверено:** 36 автотестов; браузер с временным админ-аккаунтом (удалён, настройки возвращены в «Выключено»):
валидация без курса, пересчёт порога, плашка, полоска ниже порога (45 800 → осталось 41 700), выше (39 × 2 290 →
71 448, экономия 17 862), заказ #41 (тестовый, удалён; следующий настоящий — #42) с `is_wholesale`, оптовой ценой
1 832 и строкой в WhatsApp; «своя цена» без заполненных цен не меняет цены.

**Известные ограничения:** если продавец потом уменьшит оптовый заказ ниже порога в листе заказа, цены остаются
оптовыми (решение продавца, не пересчитываются). Оптовая цена товара технически читаема покупателем напрямую из
базы (RLS товаров своего магазина) — в интерфейсе не показывается. Один порог на магазин (без уровней и филиалов).

После финального независимого ревью (0 критических, 0 серьёзных, 6 мелких): метка «Опт» и строка в WhatsApp ставятся
только если оптовые цены реально применены (`summary.applied`, порог мог набраться без единой оптовой цены);
проверка формы вынесена в `parseWholesaleInput` (тесты): процент не теряется при смене способа, при «Выключено»
порог/курс не требуются, процент строго 1–99. Отложено (мелочи): плашка на главной в режиме «своя цена» при нуле
заполненных цен всё равно пишет «цены ниже»; товар, добавленный при открытой корзине, до её перечитывания показан
по обычной цене; блок опта в «Магазине» второй раз грузит каталог ради подсчёта.
