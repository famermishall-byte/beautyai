## Новая система импорта товаров — 15.09

Старая загрузка (Каталог → выбрать файл → всё сразу заменяется) заменена на мастер:
выбор файла → определение колонок (автоматически + ручная правка) → предпросмотр →
подтверждение → импорт. Раздел: `/admin/import`, кнопка "Загрузить товары" на `/admin`.

**Архитектура (специально расширяемая под будущие форматы/магазины):**
- `src/lib/import/formats/` — парсеры конкретных форматов, каждый превращает файл в
  простую таблицу `{headers, rows}`. Сейчас только `xlsx.ts` (Excel/.xls/.xlsx). Чтобы
  добавить CSV или другой формат в будущем — один новый файл здесь + одна строка в
  `formats/index.ts`, остальной код (автоопределение колонок, валидация, сам UI) трогать
  не нужно.
- `src/lib/import/fields.ts` — список полей Beauty (Название, Цена, Артикул, Остаток,
  Бренд, Категория, Описание, Характеристики, Для кого/чего, Фото) с синонимами для
  автоопределения. Чтобы научить систему понимать новое название колонки — добавить
  строку в список алиасов нужного поля.
- `src/lib/import/autoMap.ts`, `validate.ts` — автоопределение колонок по заголовкам +
  построчная проверка (отсутствует название, некорректная цена, дубликат артикула).
  Строки с ошибками не блокируют импорт остальных — показываются отдельно.
- `src/lib/import/templates.ts` + таблица `import_templates` в Supabase — «Мои шаблоны
  импорта»: сопоставление колонок сохраняется по НАЗВАНИЯМ колонок (не по номеру), чтобы
  шаблон продолжал работать, даже если магазин добавит/переставит столбцы в своём файле.
- Импорт теперь **аддитивный** (не удаляет существующий каталог перед загрузкой, как было
  раньше) — новые товары добавляются, дубликаты по артикулу (и внутри файла, и против уже
  загруженных товаров) пропускаются с понятным сообщением.
- В `products` добавлено ограничение `unique (store_id, sku)` — гарантия на уровне базы,
  что дубли не проскочат даже при одновременных загрузках.

Протестировано вручную: файл с нарочно другими названиями/порядком колонок (Код /
Наименование товара / Производитель / Розничная цена / Кол-во / Раздел) — автоматически
распознано 5 из 6 полей, оставшееся сопоставлено вручную, сохранено как шаблон, шаблон
повторно применён при второй загрузке, проверена вся обработка ошибок (нет названия,
плохая цена, дубликат в файле, дубликат относительно каталога) — все категории сработали
корректно с точными номерами строк. Тестовые товары удалены после проверки, боевой
каталог (20 товаров) не пострадал.

## Заготовка мобильного приложения (Capacitor) — 15.09

Изначальное ТЗ (`beautyAI.docx`) описывало именно веб-сайт (Next.js + Vercel) — про
App Store/Google Play там ничего не было. Оказалось, пользователь с самого начала хотела
именно устанавливаемое мобильное приложение (недопонимание из более раннего разговора,
которого не было в контексте). Договорились: сайт не переписывать, а обернуть в
нативную оболочку (Capacitor) — так работа не теряется, а приложение просто загружает
живой сайт внутри нативного контейнера для Android/iOS.

**Что сделано (только формат/заготовка, БЕЗ публикации и БЕЗ оплаты чего-либо):**
- Установлены `@capacitor/core`, `@capacitor/cli`, `@capacitor/android`, `@capacitor/ios`.
- `capacitor.config.ts` в корне: `appId: "com.beauty.app"`, `appName: "Beauty"`,
  `server.url` указывает на боевой сайт `https://beautyai-famermishall-3772.vercel.app` —
  то есть приложение показывает ЖИВОЙ сайт (со всеми API/авторизацией/Supabase), а не
  статическую копию. Если домен когда-нибудь сменится — поменять `server.url` здесь и
  запустить `npm run cap:sync`.
- Папки `android/` и `ios/` — полноценные нативные проекты, сгенерированы и закоммичены.
- Иконки и splash-экраны сгенерированы из логотипа "B" (`assets/icon.png` — источник для
  пересборки через `npx capacitor-assets generate`, если дизайн/логотип поменяется).
- npm-скрипты: `npm run cap:sync` (пересобрать после изменений), `npm run cap:android`
  / `npm run cap:ios` (открыть нативный проект в Android Studio / Xcode).

**Чего НЕ сделано и что нужно будет пользователю для реальной публикации (когда решит
платить):**
1. **Android:** нужен Android Studio (бесплатно) на своём компьютере, чтобы открыть
   `android/` и собрать `.aab`-файл для загрузки в Google Play Console (аккаунт
   разработчика — разовый взнос $25).
2. **iOS:** сборка возможна только на Mac через Xcode, ИЛИ через облачный сервис сборки
   (например, Codemagic) — на Windows напрямую собрать `.ipa` нельзя. Плюс нужен аккаунт
   Apple Developer Program — $99/год. Apple может отклонить "обёрнутый сайт" при первой
   проверке, если не увидит ничего нативного — возможно, для прохождения ревью
   пригодится добавить push-уведомления или другую нативную фичу (не делали, не
   обсуждали детали).
3. Store-листинги (иконка, скриншоты, описание, политика конфиденциальности) — не
   готовили, когда понадобится — можно быстро сделать.
4. Ничего из вышеперечисленного не оплачено и не запущено — только техническая
   заготовка в репозитории.

**Новая концепция и структура (всё работает на обычной логике, без сети):**
- Главная (`/`) — блок "Моя кожа" + 6 карточек (Моя кожа, Проблемы кожи, Мой уход,
  Найти товар, По бюджету, Моя косметичка).
- `/skin-profile` — выбор типа кожи (5 вариантов) и проблем кожи (8 вариантов),

- `/routine` — правило-based утренний/вечерний уход, генерируется таблицей правил
  в `src/lib/skincare.ts` (тип кожи → базовый уход, проблемы → доп. советы). Никакого
  AI — простой lookup.
- `/catalog` — категории (10 фиксированных чипов), поиск по тексту, фильтр по бюджету
  (до 1000/2000/3000/5000/любой). Питается новым `/api/products` (замена AI-консультанта:
  обычный текстовый поиск + фильтры, без ИИ).
- `/mybag` ("Моя косметичка") — сохранённые товары. Новая таблица `saved_products` +
  RLS, API `/api/mybag`, клиентский `mybag-context.tsx`. Сердечко на карточке товара
  (`ProductCard`) сохраняет/убирает товар.
- `/profile` — имя, тип кожи/проблемы (+ссылка изменить), смена email/пароля (раньше
  это было только в admin/settings, теперь доступно и обычным пользователям), "Мои
  заказы", ссылки в админку (если admin/owner), "Выйти".
- Нижняя навигация (4 пункта: Главная/Каталог/Косметичка/Профиль) заменила старые
  вкладки в шапке. Шапка (`NavHeader`) теперь минимальная: название магазина + ссылка
  "Админ" (если есть права).
- Корзина (`CartDrawer`) перенесена из главной страницы в общий layout
  (`AppProviders`) — теперь доступна на любом экране, кроме `/checkout`.

**Важная попутная находка — исправлена дыра в безопасности:** политика
`profiles_update_own` в Supabase разрешала пользователю обновлять СВОЮ строку в
`profiles` без ограничения по колонкам — то есть теоретически можно было самому себе
через прямой вызов Supabase JS выставить `role='owner'`. Закрыто миграцией
`add_skin_profile_and_saved_products`: `revoke update on public.profiles from
authenticated` + `grant update (display_name, skin_type, skin_concerns) ...` — теперь
редактировать можно только безопасные поля профиля, `role`/`store_id` через этот путь
больше не поменять.

Всё протестировано вручную в браузере (регистрация тестового пользователя,
тип/проблемы кожи, уход, каталог с категориями/бюджетом, сохранение в косметичку,
корзина → оформление заказа, вход владельцем, `/admin`, `/admin/settings`).

## Регистрация/авторизация — реальные баги найдены и исправлены (14.09)
Пользователь сообщил: после нажатия "Зарегистрироваться" приложение молча кидало на
"Войти", письмо подтверждения при повторных попытках не приходило. Разобрано по логам
Supabase (`auth_logs`), найдены ДВЕ настоящие причины (не косметика):

1. **Supabase возвращает "успех" без ошибки и БЕЗ письма, если email уже
   зарегистрирован** (так задумано — защита от перебора email). Старый код не отличал
   этот случай от настоящей новой регистрации и всегда показывал "Мы отправили
   письмо…", даже когда письмо не отправлялось. Исправлено: `src/app/(auth)/login/page.tsx`
   теперь проверяет `data.user.identities.length === 0` и показывает честное сообщение
   "Этот email уже зарегистрирован. Войдите в аккаунт или восстановите пароль." —
   подтверждено вживую в браузере.
2. **Роль "owner" присваивалась первому, кто просто НАЖАЛ "Зарегистрироваться", а не
   первому, кто реально подтвердил email.** Из-за этого `eramyrza0028@gmail.com`
   (тестовая попытка, email так и не подтверждён, ни разу не логинился) навсегда занял
   `owner`, а настоящий `famermishall@gmail.com` (подтверждён, входил в систему) получил
   обычную роль `user`. Исправлено миграцией `fix_owner_assignment_on_email_confirm` в
   Supabase: `owner` теперь назначается ПОСЛЕ подтверждения email (новый триггер
   `on_auth_user_confirmed`), и роли двух существующих аккаунтов исправлены вручную
   (famermishall → owner, eramyrza → user).

Также по мелочи:
- `signUp`/`resend` теперь явно передают `emailRedirectTo` на текущий origin (раньше
  зависело только от дефолтного Site URL в Supabase).
- Добавлена проверка сессии на `/login` при загрузке страницы (`getSession()`) — если
  пользователь пришёл по ссылке подтверждения из письма (токен в URL fragment, который
  сервер/`proxy.ts` не видит), его сразу пускает в приложение вместо повторного логина.
- Регистрация с уже занятым email больше не переключает вкладку на "Войти" молча —
  показывается отдельный явный экран с понятным сообщением и кнопками.
- Экран "Проверьте почту" теперь отдельный (не общий notice) + кнопка "Отправить письмо
  ещё раз" (`supabase.auth.resend`).

**Важно про сегодняшнее тестирование:** все попытки регистрации сегодня шли через
`http://localhost:3000` (видно по `referer` в логах Supabase), НЕ через боевой сайт
Vercel — так что тестирование велось на локальном сервере разработчика.

**Всё ещё нужно проверить в Supabase Dashboard (не могу поменять программно):**
Authentication → URL Configuration:
- Site URL должен быть `https://beautyai-famermishall-3772.vercel.app`.
- Redirect URLs должны включать `http://localhost:3000/**` (для локальной разработки) И
  `https://beautyai-famermishall-3772.vercel.app/**` (боевой сайт) — без этого Supabase
  молча отклонит `emailRedirectTo` и откатится на дефолтный Site URL.
- На бесплатном тарифе действует лимит на отправку писем (уже несколько раз ловили

## Что это
Веб-приложение (сайт, работающий и на телефоне, и на компьютере) для магазина.
Покупатель пишет, что ищет, — AI подбирает товары ТОЛЬКО из реального каталога магазина.
Заказ оформляется без онлайн-оплаты и без доставки от AI: покупатель выбирает филиал,
оставляет имя/телефон, и заказ уходит продавцу в WhatsApp этого филиала.

Приложение закрыто авторизацией: без входа в систему интерфейс вообще не открывается —
сначала экран входа/регистрации.

## Система авторизации и ролей

### Модель данных
- `auth.users` — встроенная таблица Supabase Auth (email, пароль).
- `public.profiles` — по одной строке на пользователя: `role` (`user` | `admin` | `owner` |
  `super_admin`), `store_id`. Создаётся триггером `handle_new_user` (AFTER INSERT ON
  auth.users) с ролью `user` по умолчанию.
- **Владельцем (`owner`) становится первый пользователь, который ПОДТВЕРДИЛ email**
  (не просто нажал "Зарегистрироваться") — назначается триггером `on_auth_user_confirmed`
  (AFTER UPDATE ON auth.users, когда `email_confirmed_at` становится не-null), см. раздел
  про исправление багов выше. Все следующие подтверждённые пользователи — обычные `user`.
- Роли `admin` и `owner` обе дают доступ к `/admin`; только `owner` может передать
  владение магазином другому человеку (важно для будущей продажи системы разным
  магазинам — см. ниже).

### Разграничение доступа — по-настоящему, не только в интерфейсе
1. `src/proxy.ts` (замена middleware.ts в Next.js 16) — на каждый переход по странице
   проверяется сессия Supabase. Нет сессии → редирект на `/login`.
2. `src/app/(app)/admin/layout.tsx` — серверная проверка роли на КАЖДЫЙ запрос к
   `/admin/*`. Не admin/owner → редирект на `/?denied=admin` (баннер "Доступ запрещён").
3. Каждый API-маршрут сам проверяет сессию (`getSessionProfile()`) и сам определяет
   `store_id` пользователя — клиент не может передать чужой storeSlug.
4. RLS-политики в самой базе данных (последняя линия защиты): товары/филиалы/заказы
   видны только своему магазину; писать могут только admin/owner своего магазина.

### Экраны
- `/login` — одна страница, три вкладки (Войти / Регистрация / Забыли пароль).
- `/reset-password` — по ссылке из письма, форма нового пароля.
- Splash-экран (0.9 сек) с названием магазина при каждом входе/открытии приложения.
- `/admin/settings` — смена email (с подтверждением по почте), смена пароля, и (только
  у owner) передача владения магазином другому зарегистрированному пользователю по email.

### Передача владения магазином (для продажи разным клиентам в будущем)
SQL-функция `transfer_store_ownership(new_owner_email)` в Supabase: владелец вводит email
УЖЕ зарегистрированного человека — тот становится owner магазина, прежний владелец
полностью теряет доступ (role→user, store_id→null). Так тестовый аккаунт (моя личная
почта) можно будет безопасно "отвязать" после продажи, не трогая код/базу вручную.
Ограничение: новый владелец должен СНАЧАЛА сам зарегистрироваться (нет доступа к
Supabase Admin API, чтобы создавать аккаунты за других людей).
