## 📌 СНИМОК ПРОЕКТА (читать первым; всё ниже — подробности по этапам)

**Статус:** приложение почти готово, владелец показывает его клиентам. Впереди: выбор языка (позже), затем
оставшиеся важные пункты (см. «Что дальше»). Всё сохранено: код — в git (`main`, метка `v0.9-showcase`),
сайт — Vercel (`https://beautyai-famermishall-3772.vercel.app`, выкладывается сам из `main`),
мобильная версия — Capacitor-оболочка (`capacitor.config.ts`, `android/`, `ios/`), которая ЗАГРУЖАЕТ тот же
живой сайт по HTTPS → сайт, PWA и приложение всегда идентичны, отдельной копии нет (после правок ничего
синхронизировать не нужно; `npm run cap:sync` — только если меняется конфиг/плагины/иконки). База — Supabase
(проект `nufmsvwkixnfjvzdabmz`).

**Что есть (кратко):** витрина (каталог: 14 категорий × 103 подкатегории, фильтры, «Хиты», скидки, «Акции»,
плавающая корзина на каждой странице, кнопка «назад» везде); ~290 демо-товаров `DEMO-*` с фото (постоянные
demo-данные — не удалять); вход/роли (владелец, администратор, управляющий филиала, покупатель; один аккаунт —
два режима «Админка/В магазин»); админка-меню из иконок (остатки по филиалам, заказы-очередь, филиалы по
городам, сотрудники, загрузка товаров, каталог, обратная связь, магазин, аккаунт); заказы: одна ссылка продавцу
в WhatsApp → мини-страница (убрать то, чего нет, «Оплата получена», отмена), автообновление у админа и покупателя,
продажи по филиалам/всем филиалам, проверка наличия при оформлении. Оплата и доставка — вне приложения
(продавец в WhatsApp, деньги на расчётный счёт продавца).

**SQL в Supabase (запущены владельцем; порядок при развёртывании с нуля, файлы в `supabase/`):**
1. (ранние миграции самой системы — таблицы `stores/profiles/branches/products/product_branch_stock/orders/feedback…`,

## Реальный логотип клиента — 20.09

Клиент прислал файл логотипа "ОПТОВЫЕ ЦЕНЫ 01" — `design/logo-drafts/0-reference.jpg`
(JPEG 223×233, максимальное качество, которое есть). Пробовал сначала перерисовать его
вручную в чистый SVG (несколько итераций, рендерил и сверял визуально через `sharp`) —
получилось похоже, но не идентично (форма завитков). Пользователь решил: не перерисовывать,
использовать сам оригинальный файл как источник изображения везде, где раньше был
`BrandMark.tsx` со сплошным SVG.

**Что сделано:**
- `scripts/build-brand-assets.mjs` — единый скрипт на `sharp`, паддит исходник до квадрата
  фирменным розовым (`#c8135f`) и экспортирует нужные размеры: `public/brand/mark.png`
  (256, для `BrandMark.tsx`), `src/app/icon.png` (512, favicon), `src/app/apple-icon.png`
  (180), `public/icon-512.png` (512, PWA-манифест), `assets/icon.png` +
  `assets/icon-foreground.png` (1024, источник для Capacitor). Перезапускать при
  необходимости: `node scripts/build-brand-assets.mjs`.
- `BrandMark.tsx` теперь рендерит `next/image` с `/brand/mark.png` вместо SVG-фигур
  (проп `color` убран — он больше не нужен, картинка уже содержит цвет).
- Удалены `src/app/icon.tsx` и `src/app/apple-icon.tsx` (динамические `ImageResponse`-роуты) —
  заменены статическими файлами по конвенции Next.js (`icon.png`/`apple-icon.png` в
  `src/app/`). `manifest.ts` теперь ссылается на `/icon-512.png` вместо старого `/icon`.
- **Важный побочный баг, который заодно поправили**: `src/proxy.ts` (middleware) редиректил
  на `/login` вообще все запросы, не входящие в явный список исключений — новый путь
  `/brand/mark.png` под это попадал, из-за чего сам логотип не показывался
  неавторизованному пользователю (в т.ч. на самой странице входа). Добавили `brand` в
  matcher-исключения. Стоит помнить на будущее: любой новый статический ассет вне
  `public`-путей, уже перечисленных в matcher, будет так же блокироваться.
- Апскейл: источник всего 223×233, поэтому 512px-иконки (favicon, PWA) выглядят мягко/слегка
  размыто при увеличении — осознанный компромисс по решению пользователя (лучше настоящий
  логотип чуть мягкий, чем точная перерисовка). Проверено сборкой (`npm run build`) и
  визуально в браузере (страница входа, Playwright-скриншот) — выглядит нормально.
- `assets/splash.png`/`splash-dark.png` (сплэш-экран Capacitor) — тоже обновлены (см. ниже),
  были не тронуты даже во время ребрендинга 15.09 и до сих пор показывали старый
  коричневый "B" от самого первого варианта бренда "Beauty".
- Пришлось поправить сам скрипт: первая версия накладывала квадратный кусок с
  собственным запечённым розовым фоном на такой же розовый канвас — из-за JPEG-шума
  оттенки чуть-чуть не совпадали, был заметен шов-прямоугольник вокруг марки. Исправлено:
  скрипт сначала вырезает белое кольцо через альфа-маску по яркости пикселя (порог
  130–210, с плавным краем, не хардкод-трешолд) — получается прозрачная PNG-марка без
  собственного фона, её уже кладём на любой нужный цветной канвас без швов.
- `npx capacitor-assets generate` запущен (20.09) — перегенерировал 118 android-файлов
  (иконки всех плотностей + light/dark сплэши) и 13 ios-файлов (AppIcon, Splash.imageset
  light/dark). Визуально сверил один android- и один ios-файл — логотип на месте, без шва.
  **Побочный эффект, на который стоит обратить внимание при следующем запуске**: команда
  заодно генерирует ненужный "pwa"-таргет — папку `icons/` в корне репозитория и
  `public/manifest.webmanifest`. Второе особенно коварно: статический файл в `public/`

## Новая система импорта товаров — 15.09

Старая загрузка (Каталог → выбрать файл → всё сразу заменяется) заменена на мастер:
выбор файла → определение колонок (автоматически + ручная правка) → предпросмотр →
подтверждение → импорт. Раздел: `/admin/import`, кнопка "Загрузить товары" на `/admin`.

**Архитектура (специально расширяемая под будущие форматы/магазины):**
- `src/lib/import/formats/` — парсеры конкретных форматов, каждый превращает файл в
  простую таблицу `{headers, rows}`. Сейчас только `xlsx.ts` (Excel/.xls/.xlsx). Чтобы
  добавить CSV или другой формат в будущем — один новый файл здесь + одна строка в
  `formats/index.ts`, остальной код (автоопределение колонок, валидация, сам UI) трогать
  не нужно.
- `src/lib/import/fields.ts` — список полей Beauty (Название, Цена, Артикул, Остаток,
  Бренд, Категория, Описание, Характеристики, Для кого/чего, Фото) с синонимами для
  автоопределения. Чтобы научить систему понимать новое название колонки — добавить
  строку в список алиасов нужного поля.
- `src/lib/import/autoMap.ts`, `validate.ts` — автоопределение колонок по заголовкам +
  построчная проверка (отсутствует название, некорректная цена, дубликат артикула).
  Строки с ошибками не блокируют импорт остальных — показываются отдельно.
- `src/lib/import/templates.ts` + таблица `import_templates` в Supabase — «Мои шаблоны
  импорта»: сопоставление колонок сохраняется по НАЗВАНИЯМ колонок (не по номеру), чтобы
  шаблон продолжал работать, даже если магазин добавит/переставит столбцы в своём файле.

  загруженных товаров) пропускаются с понятным сообщением.
- В `products` добавлено ограничение `unique (store_id, sku)` — гарантия на уровне базы,
  что дубли не проскочат даже при одновременных загрузках.

## Регистрация/авторизация — реальные баги найдены и исправлены (14.09)
Пользователь сообщил: после нажатия "Зарегистрироваться" приложение молча кидало на
"Войти", письмо подтверждения при повторных попытках не приходило. Разобрано по логам
Supabase (`auth_logs`), найдены ДВЕ настоящие причины (не косметика):

1. **Supabase возвращает "успех" без ошибки и БЕЗ письма, если email уже
   зарегистрирован** (так задумано — защита от перебора email). Старый код не отличал
   этот случай от настоящей новой регистрации и всегда показывал "Мы отправили
   письмо…", даже когда письмо не отправлялось. Исправлено: `src/app/(auth)/login/page.tsx`
   теперь проверяет `data.user.identities.length === 0` и показывает честное сообщение
   "Этот email уже зарегистрирован. Войдите в аккаунт или восстановите пароль." —
   подтверждено вживую в браузере.
2. **Роль "owner" присваивалась первому, кто просто НАЖАЛ "Зарегистрироваться", а не
   первому, кто реально подтвердил email.** Из-за этого `eramyrza0028@gmail.com`
   (тестовая попытка, email так и не подтверждён, ни разу не логинился) навсегда занял
   `owner`, а настоящий `famermishall@gmail.com` (подтверждён, входил в систему) получил
   обычную роль `user`. Исправлено миграцией `fix_owner_assignment_on_email_confirm` в
   Supabase: `owner` теперь назначается ПОСЛЕ подтверждения email (новый триггер
   `on_auth_user_confirmed`), и роли двух существующих аккаунтов исправлены вручную
   (famermishall → owner, eramyrza → user).

Также по мелочи:
- `signUp`/`resend` теперь явно передают `emailRedirectTo` на текущий origin (раньше
  зависело только от дефолтного Site URL в Supabase).
- Добавлена проверка сессии на `/login` при загрузке страницы (`getSession()`) — если

## Что это
Веб-приложение (сайт, работающий и на телефоне, и на компьютере) для магазина.
Покупатель пишет, что ищет, — AI подбирает товары ТОЛЬКО из реального каталога магазина.

оставляет имя/телефон, и заказ уходит продавцу в WhatsApp этого филиала.

Приложение закрыто авторизацией: без входа в систему интерфейс вообще не открывается —
сначала экран входа/регистрации.

## Система авторизации и ролей

### Модель данных
- `auth.users` — встроенная таблица Supabase Auth (email, пароль).
- `public.profiles` — по одной строке на пользователя: `role` (`user` | `admin` | `owner` |
  `super_admin`), `store_id`. Создаётся триггером `handle_new_user` (AFTER INSERT ON
  auth.users) с ролью `user` по умолчанию.
- **Владельцем (`owner`) становится первый пользователь, который ПОДТВЕРДИЛ email**
  (не просто нажал "Зарегистрироваться") — назначается триггером `on_auth_user_confirmed`
  (AFTER UPDATE ON auth.users, когда `email_confirmed_at` становится не-null), см. раздел
  про исправление багов выше. Все следующие подтверждённые пользователи — обычные `user`.
- Роли `admin` и `owner` обе дают доступ к `/admin`; только `owner` может передать
  владение магазином другому человеку (важно для будущей продажи системы разным
  магазинам — см. ниже).

### Разграничение доступа — по-настоящему, не только в интерфейсе
1. `src/proxy.ts` (замена middleware.ts в Next.js 16) — на каждый переход по странице
   проверяется сессия Supabase. Нет сессии → редирект на `/login`.
2. `src/app/(app)/admin/layout.tsx` — серверная проверка роли на КАЖДЫЙ запрос к
   `/admin/*`. Не admin/owner → редирект на `/?denied=admin` (баннер "Доступ запрещён").
3. Каждый API-маршрут сам проверяет сессию (`getSessionProfile()`) и сам определяет
   `store_id` пользователя — клиент не может передать чужой storeSlug.
4. RLS-политики в самой базе данных (последняя линия защиты): товары/филиалы/заказы
   видны только своему магазину; писать могут только admin/owner своего магазина.

### Экраны
- `/login` — одна страница, три вкладки (Войти / Регистрация / Забыли пароль).
- `/reset-password` — по ссылке из письма, форма нового пароля.
- Splash-экран (0.9 сек) с названием магазина при каждом входе/открытии приложения.
- `/admin/settings` — смена email (с подтверждением по почте), смена пароля, и (только
  у owner) передача владения магазином другому зарегистрированному пользователю по email.

### Передача владения магазином (для продажи разным клиентам в будущем)
SQL-функция `transfer_store_ownership(new_owner_email)` в Supabase: владелец вводит email
УЖЕ зарегистрированного человека — тот становится owner магазина, прежний владелец
полностью теряет доступ (role→user, store_id→null). Так тестовый аккаунт (моя личная
почта) можно будет безопасно "отвязать" после продажи, не трогая код/базу вручную.
Ограничение: новый владелец должен СНАЧАЛА сам зарегистрироваться (нет доступа к
Supabase Admin API, чтобы создавать аккаунты за других людей).

## Роли: управляющий филиала, сотрудники, один аккаунт — два режима (21.09)
- Роли: `owner` (всё), `admin` (весь магазин, кроме «Сотрудников»), **`branch_manager`** (только свой
  филиал: остатки и заказы + «Аккаунт»), `user` (покупатель). Новые люди всегда `user`; доступ выдаёт
  только владелец в разделе **«Сотрудники»** (`/admin/staff`, `/api/admin/staff`): вводит почту
  (человек должен сначала сам зарегистрироваться) + роль + филиал; «Снять доступ» → снова `user`.
- БД: `supabase/staff_roles.sql` (ЗАПУСТИТЬ в SQL Editor, без переводчика браузера): колонка
  `profiles.branch_id`, роль `branch_manager` в check-ограничении, функции `staff_list` /
  `staff_set` (security definer, только владелец, сообщения об ошибках по-русски), RLS-политики
  «управляющий видит/правит остатки и заказы только своего филиала», триггер, сам пересчитывающий
  `products.in_stock` при изменении остатков (управляющий не может править таблицу товаров).
  Код читает `branch_id` отдельным запросом только для `branch_manager`, поэтому вход не ломается,
  даже если SQL ещё не запущен.
- Проверки на сервере: `isStaff(role)` (auth.ts) пускает в админку; в `/api/admin/stock` и
  `/api/admin/orders` управляющий принудительно ограничен своим `branchId` (что бы ни прислал клиент);
  остальные админ-API по-прежнему только `owner/admin`. `proxy.ts`: управляющему доступны лишь
  `/admin`, `/admin/stock`, `/admin/orders`, `/admin/settings`; `admin` не открывает `/admin/staff`.
- **Один аккаунт — два режима** (вопрос владельца: у людей одна почта и они хотят и работать, и
  покупать): сотрудник по кнопке «В магазин» (шапка админки) видит витрину как покупатель, по кнопке
  «Админка» возвращается. Реализация: cookie `beautyai-mode=shop` (`src/lib/view-mode.ts`) только
  разрешает `proxy.ts` открывать витрину; реальные права всегда по роли в БД. `isAdmin` в
  `session-context` теперь = «сотрудник на /admin/*», `isManager` = «у человека есть роль сотрудника».
  Заказы, сделанные в режиме покупателя, привязаны к его `user_id` как обычные.

## Корзина везде, статусы оплаты/курьера и итоги продаж (21.09)
- **Плавающая корзина** (`CartDrawer.tsx`) теперь на КАЖДОЙ странице витрины, включая карточку товара

- **Цепочка статусов** (`src/lib/orderStatus.ts`): Новый → Подтверждён → **Оплачен** → **Передан курьеру**
  → Выполнен (или Отменён). Оплата и курьер идут вне приложения, поэтому филиал отмечает шаги сам:
  в админке кнопка «следующий шаг» (Подтвердить → Отметить оплаченным → Передан курьеру → Заказ
  доставлен) + выпадающий список, а в WhatsApp-сообщении филиалу теперь пять ссылок (одно нажатие —
  статус обновился без входа). «Автоматически» без интеграции с платёжной/курьерской системой не
  получится — это возможный следующий этап, когда станет известно, чем они пользуются.
- **Продажи** = заказы со статусом «Оплачен», «Передан курьеру», «Выполнен» (новые, неоплаченные и
  отменённые не входят). Блок «Продажи» вверху страницы заказов: период (сегодня / 7 / 30 дней / всё
  время), итоговая сумма и число заказов. Управляющий филиала видит продажи только своего филиала;
  владелец/админ — все филиалы: таблица «филиал → заказов → сумма» и «Итого по всем филиалам».
  Дата продажи = `paid_at` (если нет — дата создания).
- Заказы: фильтры по статусу (с числами) и, для владельца/админа, по филиалу; пагинация по 30.
- БД: `supabase/order_payments.sql` (ЗАПУСТИТЬ): колонки `orders.paid_at`/`shipped_at`, новое
  ограничение статусов, функция `set_order_status_by_token` для ссылок из WhatsApp. Код работает и до
  запуска (старые статусы, три старые ссылки), но «Оплачен/Передан курьеру» заработают только после SQL.

- **Как платят и оформляют (решение владельца, 21.09):** покупка и оплата — только через продавца в WhatsApp,
  деньги идут напрямую на расчётный счёт продавца; доставка — на продавце, в приложении её не ведём.
  Поэтому продавец отмечает заказ **одной ссылкой прямо в чате WhatsApp** (в сообщении три ссылки:
  «Подтвердить», «Оплата получена», «Отменить») → статус сразу появляется у администратора и управляющего
  филиала; «Оплачен» = продажа. Экран заказов сам обновляется каждые 20 с (и при возврате на вкладку),
  бейдж «новых заказов» на главной админки — каждые 30 с. В заказе видно, кто и когда отметил статус
  («отметил продавец в WhatsApp» / «отмечено в приложении») — колонки `orders.status_source`,
  `status_changed_at` (в `order_payments.sql`, безопасно перезапускать). Цепочка в админке:
  Новый → Подтверждён → Оплачен → Выполнен; «Передан курьеру» остался необязательным статусом.
  Идея на будущее: WhatsApp Business API (продавец отвечает словом «оплачен» — статус меняется сам) —
  платно и требует одобрения Meta; сейчас не нужно.

## «Очередь заказов»: одна ссылка продавцу, изменение состава, наличие по позициям (21.09)
- Решения владельца (все три «да»): (1) вместо набора ссылок в WhatsApp — **одна ссылка** `/o/<token>`;
  (2) после «Оплата получена» состав **блокируется** (правит только администратор в приложении);
  (3) когда продавец ставит товару 0 — **остаток этого товара в этом филиале автоматически становится 0**
  (только число в приложении; учётная программа не меняется, следующая загрузка Excel может вернуть число —
  продавцу нужно поправить и у себя).
- **Мини-страница продавца** (`/o/<token>`, `OrderConsole.tsx`, API `/api/o/[token]`): состав с кнопками −/+

  получена», «Отменить», «Написать покупателю об изменениях» (WhatsApp с готовым текстом и новой суммой).
  Правила и запись — в SQL-функциях `get_order_by_token` / `edit_order_by_token` (`supabase/order_edit.sql`):
  нельзя добавлять/менять цену, нельзя после оплаты, если убрано всё — заказ отменяется. Старые ссылки
  `/o/<token>/<status>` продолжают работать.
- Данные заказа: позиции хранят `orderedQuantity` (заказано), `productId`, `sku`; `orders.original_total`,
  `edited_at`, `edited_by`. Везде показывается ИТОГОВАЯ сумма: у покупателя («Мои покупки»: убранное
  зачёркнуто «нет в наличии», «было X, стало Y»), у админа/управляющего, в итогах продаж.
- **Админ/управляющий** (`OrderManager.tsx`): рабочая очередь «Требуют действия» (старые сверху), группа «Нет в
